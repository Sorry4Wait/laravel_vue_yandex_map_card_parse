# Интеграция с Яндекс.Картами — тестовое задание

Laravel (API) + Vue 3 (SPA, Composition API). Подключаешь ссылку на карточку организации
на Яндекс.Картах, бэкенд парсит отзывы и рейтинг в фоне через очередь, фронт показывает
результат с пагинацией.

## Стек и структура

```
backend/                          Laravel 12, API-only, Sanctum (SPA cookie auth)
backend/scripts/yandex_reviews/   Python + Playwright скрапер отзывов (см. "Как устроен парсинг")
frontend/                         Vue 3 + TypeScript, Vite, vue-router
docker/                           Dockerfile для php-fpm (плюс python3/playwright/chromium), конфиг nginx
docker-compose.yml
```

## Как поднять локально

Нужен только Docker.

```bash
git clone <repo>
cd <repo>
cp backend/.env.example backend/.env   # уже есть подготовленный backend/.env — можно и его оставить
docker compose up -d --build
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
docker compose exec app php artisan db:seed
```

Сервисы:

- фронт — [http://localhost:5173](http://localhost:5173)
- API — [http://localhost:8000](http://localhost:8000)
- mysql — localhost:3306 (laravel / secret)

Очередь (`queue`) и nginx поднимаются автоматически вместе с остальными сервисами через
`docker compose up -d`.

Логин для теста (сидится сидером, регистрации в задании нет):

```
demo@example.com / password
```

## Переменные окружения

Смотри `backend/.env.example` — там всё стандартное для Laravel плюс блок в конце:

```
YANDEX_PARSER_DRIVER                        playwright (по умолчанию, все отзывы) или http (только первые ~50, без браузера)
YANDEX_PYTHON_BIN / YANDEX_SCRAPER_TIMEOUT_SECONDS   каким python'ом и сколько ждать скрапер
YANDEX_PARSER_MIN_DELAY_MS / MAX_DELAY_MS   задержка между запросами к Яндексу (http-драйвер)
YANDEX_PARSER_PROXIES                       список прокси через запятую, можно пусто
SANCTUM_STATEFUL_DOMAINS / FRONTEND_URL     под какой домен фронта настроена SPA-аутентификация
```

## Аутентификация

Sanctum в SPA-режиме (cookie + CSRF), не токены. Фронт сначала бьёт
`GET /sanctum/csrf-cookie`, потом `POST /api/login` с email/паролем — дальше все запросы
идут с сессионной кукой. `bootstrap/app.php` подключает `statefulApi()`, домены заданы в
`SANCTUM_STATEFUL_DOMAINS`.

## Как устроен парсинг

Код лежит в `backend/app/Services/YandexMaps/`, два фетчера за одним интерфейсом
`ReviewsFetcherContract`, драйвер выбирается через `YANDEX_PARSER_DRIVER`:

- `OrgUrlResolver` — валидирует, что ссылка похожа на карточку Яндекс.Карт (принимает
любой домен вида `yandex.<что угодно>`, потому что Яндекс гео-редиректит на
страновые домены — `.ru`, `.uz`, `.kz`...), вытаскивает `businessId` из URL и
резолвит короткие ссылки (`/maps/-/xxx`) через редирект.
- `AntiBanHttpClient` — обёртка над http-клиентом: рандомный User-Agent на запрос,
случайная задержка перед каждым запросом, опциональная ротация прокси, ретраи с
backoff при 5xx/timeout, отдельная обработка 403/429/капчи как блокировки.
- `ReviewsFetcher` (`YANDEX_PARSER_DRIVER=http`) — дёргает `{orgUrl}/reviews/` плейн
GET'ом и вытаскивает инлайновый JSON-стейт, который Яндекс зашивает в HTML при
SSR (`extractEmbeddedState()`, ищет узел с `ratingData`+`reviewResults`). Без  
браузера, но отдаёт только первую партию — обычно 50.
- `PlaywrightReviewsFetcher` (`YANDEX_PARSER_DRIVER=playwright`, по умолчанию) —
шеллится в `backend/scripts/yandex_reviews/scrape_reviews.py`, который открывает
карточку в headless Chromium и скроллит панель отзывов до конца, забирая их все.
Возвращает один JSON с агрегатами и всеми отзывами, раскладывает его по тем же
callback'ам, что и http-фетчер — джоба не знает и не должна знать, какой из двух
реально ходил в Яндекс.
- `ParseOrganizationReviewsJob` — очередь-джоба: апсертит отзывы, ведёт статус запуска,
сохраняет агрегаты организации.

**Почему браузер, а не внутренний API.** У кастомного скролл-виджета Яндекса подгрузка
привязана к разбору «show more» через `/maps/api/business/fetchReviews` — путь и
csrf-токен реверс-инжинирятся, но там есть параметр `s`, похожий на клиентскую подпись
запроса, а сам расчёт лежит в JS-чанке, который подгружается лениво. Раскапывать это
дальше — постоянная гонка с Яндексом (поменяют алгоритм — всё сломается без
предупреждения). Браузер обходит это вообще, потому что выполняет настоящий JS
Яндекса, а не имитирует его: скрипт не диспатчит синтетическое scroll-событие
(WebDriver-навигация Selenium на это натыкалась — виджет игнорировал её как
"untrusted"), а сразу присваивает `container.scrollTop = container.scrollHeight` — это
настоящее действие браузера, и на него движок сам генерирует trusted `scroll`, которого
и ждёт ленивая подгрузка. Плюс живой User-Agent/viewport и скрытый
`navigator.webdriver`, иначе Яндекс сразу отдаёт антибот-заглушку вместо страницы.
Компромисс — медленнее http-варианта (открыть браузер, проскроллить) и требует
Chromium в инфраструктуре (см. `docker/php/Dockerfile`).

Итог: с `playwright`-драйвером организация получает точные агрегаты и все реально
существующие отзывы. С `http` — только агрегаты и первые ~50

## Доп. требования

**1. Устойчивость к смене разметки.**
Оба фетчера кидают `YandexSourceChangedException`, а не молча возвращают пустоту.
`ReviewsFetcher`: инлайновый json-стейт вообще не парсится (`extractEmbeddedState()`),
в нём нигде не находится узел с `ratingData`+`reviewResults` (`findOrgCardNode()`), или
у конкретного отзыва нет вообще ни одного из ожидаемых полей (`normalizeReview()`).
`PlaywrightReviewsFetcher` — то же самое на своём уровне: python-скрипт вернул
невалидный JSON или JSON без ключа `reviews`, либо конкретный отзыв пустой по всем
полям. Джоба ловит это исключение отдельно от сетевых ошибок, помечает
`parse_runs.failure_reason = source_changed`, логирует `Log::critical` и **не ретраит** —
ретраить смысла нет, если сломался парсер, а не сеть.

**2. Обоснование подхода к парсингу.** См. раздел выше.

**3. Масштаб и фоновая обработка.**
Парсинг идёт через Laravel-очередь (`ParseOrganizationReviewsJob`, redis-драйвер,
отдельный контейнер `queue`). Прогресс виден в реальном времени — `parse_runs.status` +
`reviews_fetched` обновляется после каждой скачанной страницы, фронт поллит
`GET /api/organizations/{id}/parse-status` раз в 2 секунды, пока статус не станет
`succeeded`/`failed`. Ретраи — 3 попытки с backoff `[10, 30, 90]` секунд на уровне джобы
(на транзиентные `YandexBlockedException`/`YandexUnavailableException`), плюс отдельные
ретраи внутри самого http-клиента на уровне одного запроса.

**4. Анти-бан на объёме.**
У http-фетчера это `AntiBanHttpClient`: случайная пауза 0.8–2.2с перед каждым запросом
(настраивается через env), ротация User-Agent из пула, опциональная ротация прокси
(`YANDEX_PARSER_PROXIES`), экспоненциальный backoff с джиттером при 5xx/429/детекте
капчи. У playwright-фетчера свой набор: живой User-Agent/viewport вместо дефолтного
headless-отпечатка, скрытый `navigator.webdriver`, случайная пауза 1.5–2.3с между
скроллами. Обе стороны различают "нас заблокировали" от обычной недоступности —
`YandexBlockedException` против `YandexUnavailableException` — джоба ретраит второе и
не ретраит первое так же слепо (у обоих 3 попытки с backoff `[10, 30, 90]` на уровне
джобы, но статус `parse_runs.failure_reason` разный, и это видно в интерфейсе). 

**5. Идемпотентность и история изменений.**
Организация уникальна по `yandex_url` — повторное сохранение той же ссылки не создаёт
вторую запись, просто перезапускает парсинг. Отзыв уникален по
`(organization_id, external_id)`, где `external_id` — либо реальный id отзыва от
Яндекса, либо хэш от автора+текста+даты, если Яндекс id не отдаёт — так что реимпорт не
плодит дубли. Если при повторном парсинге текст или оценка у уже существующего отзыва
изменились (люди правда иногда редактируют отзывы), старое значение уходит в
`review_revisions` перед обновлением — там прям видно "было → стало" по каждому
изменившемуся отзыву. На уровне организации то же самое даёт `parse_runs`: там пишется снапшот агрегатов (рейтинг/число оценок/число отзывов) на момент каждого запуска.

## Пагинация и кэширование

Отзывы отдаются со своей базы (`GET /api/organizations/{id}/reviews?page=N`), а не
перепарсиваются на каждый клик по пагинации — иначе 12 кликов по страницам это 12 полных
прогонов парсинга по ~600 отзывов, и организацию, если у неё правда 600 отзывов, вообще
нельзя было бы посмотреть без пары минут ожидания на каждой странице. Парсинг — фоновая
джоба, которая один раз наполняет базу, а листание — обычный `paginate()` по уже
сохранённым данным. Повторный парсинг (например, руками с настроек) просто обновляет то,
что изменилось, без даунтайма для того, что уже отображается.
